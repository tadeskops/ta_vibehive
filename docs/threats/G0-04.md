# Threat model · Slice G0-04 (Client-side identity + role + rate limit)

Per `AGENTS.md §4.1`: every module ships with a five-line threat model.

1. **Assets in scope.** `assets/js/identity.js` (localStorage-backed name/flat/anonymous), `assets/js/ratelimit.js` (per-bucket hourly counter). Both are client-only; nothing on GitHub Pages talks to a server yet.
2. **Trust boundaries.** Browser JS ↔ localStorage. No network calls in this slice. The server-side boundary (Actions writing to the data repo) will re-check every field and re-enforce a real rate limit; the client is UX-only.
3. **Top risks.** (a) An attacker clears `localStorage` to bypass the client rate limit — mitigated by GitHub's own API rate limit + a per-repo Action-side counter that will land in G1-04 (documented as follow-up here). (b) An attacker forges a committee token — mitigated because the token is opaque; it only unlocks committee UI, and the server-side verify (G1-04) checks the token's GitHub App audience + expiry. (c) Identity fields injected with control characters — mitigated by strict flat regex + name length cap; all render paths use Alpine `x-text` (no `x-html`). (d) Cross-tab race on the rate-limit counter — accepted (counter may over-count by 1 in a rare race; still bounded).
4. **Assumptions.** localStorage is per-origin isolated (Pages TLS). No sub-origin embeds this app. Modern browsers only (ES2020+). Nobody trusts the browser's role claim to grant a real permission — every write path re-checks server-side.
5. **Follow-ups.** (a) Add server-side rate limit (Action-side counter file in the data repo) in G1-04. (b) Add GitHub App device flow in G1-04. (c) Add unit test for identity XSS attempts once the write path exists.
