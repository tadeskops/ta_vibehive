# Threat model · Slice G1-01 (Ganpati event page)

1. **Assets in scope.** Public route `/g/ganpati-2026/` reading `config/ganpati_2026.json` on the same origin. Validator + formatters in `assets/js/event.js`; Alpine bootstrap in `assets/js/event-init.js`.
2. **Trust boundaries.** Browser ↔ same-origin static JSON. No user input on this page (read-only). The JSON is authored by the committee via a PR against the app repo (later: private data repo in G1-04).
3. **Top risks (OWASP mapped).** A03 XSS via config → mitigated: values rendered via Alpine `x-text` only (never `x-html`); no dangerouslySetInnerHTML equivalents; strict CSP inherited from index shell. A05 config injection via git PR → mitigated: schema-strict validator rejects unknown-shape input; every field type-checked with min/max bounds. A08 config tampering → mitigated: change history is git commit log (any edit is a signed commit under identity lock). A04 SSRF → N/A (no server, `fetch()` locked to same origin by `connect-src 'self'`). A06 vulnerable components → mitigated by SRI on Alpine.
4. **Assumptions.** Config PR merges require committee identity (enforced by G1-04's device-flow committee auth, not by this slice). Until then, only tadeskops can push per the local identity-lock hooks. JSON parser = browser-native `JSON.parse`; no custom parser attack surface.
5. **Follow-ups.** (a) When multiple events exist (G3-01), add a `config/events.index.json` allow-list check so an event page cannot pull an arbitrary config path. (b) Add contrast auto-check for cluster tints in G3. (c) Add config-schema unit test in the data repo when it ships (G1-04). (d) Consider signed-manifest for config on Pages if a second maintainer joins post-launch.
