# Threat model · Slice G1-02 (Contribute form)

1. **Assets in scope.** `assets/js/contribute.js` (validator + draft persistence + Alpine component), `assets/js/contribute-init.js` (Alpine bootstrap), `g/ganpati-2026/contribute/index.html` (form page).
2. **Trust boundaries.** Browser only. No network I/O apart from same-origin config fetch. Draft persisted in `localStorage.tvh.contrib.draft`. Identity persisted in `localStorage.tvh.identity` (G0-04).
3. **Top risks (OWASP mapped).** A03 injection via draft tampering → mitigated: `readDraft` requires exact type shape and returns `null` on any mismatch; amount re-validated on next screen (G1-03) so a tampered draft cannot skip validation. A04 amount tampering (client trust) → acknowledged: the client value is authoritative only for UX; real amount is enforced server-side by G1-04's committee-verify workflow before receipt issuance. A05 flooding submissions → mitigated: G0-04 `checkRate` bucket `contribute-<eventId>` capped at 6/hour per browser. A03 XSS via identity name → mitigated: name rendered nowhere in this slice; when it lands on the dashboard (G2) it will be `x-text` only. A01 access control → N/A (public contribution page by design).
4. **Assumptions.** localStorage is per-origin (browser guarantees). CSP `default-src 'self'` prevents third-party script injection. `form-action 'self'` prevents cross-origin form POST hijack. The rate limiter is UX-only and can be bypassed by clearing storage; real duplicate-submission defense lives in G1-04 (UTR uniqueness).
5. **Follow-ups.** (a) In G1-04, enforce server-side amount range check when the workflow processes the submission PR. (b) In G1-04, enforce UTR uniqueness so a bypassed client rate limit cannot double-record. (c) Consider CAPTCHA if abuse is observed post-launch. (d) When identity capture becomes verified email in G-2 post-launch, migrate draft schema with a version tag.
