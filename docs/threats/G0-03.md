# Threat model · Slice G0-03 (Audit-log-lite)

Per `AGENTS.md §4.1`: every module ships with a five-line threat model.

1. **Assets in scope.** `assets/js/audit.js` (append + verify + canonicalize + chain-fingerprint), `tests/audit.test.js`. Future Action workflows will import this module (bundled into a workflow-scope script) to write entries into `audit/<yyyy-mm>.json` in the private data repo.
2. **Trust boundaries.** GitHub Action (write path, uses a fine-grained deploy token scoped only to the private data repo) ↔ private data repo git history. Public visitors read only the tail-hash fingerprint via a static JSON exported to Pages; they never see the log body.
3. **Top risks.** (a) Silent tamper of a middle entry — mitigated by SHA-256 chain: any edit breaks the chain from that point (test suite `tampering with an entry.meta`). (b) Entry deletion — mitigated by monotonic seq check (`deleting a middle entry`). (c) Attacker recomputes tampered entry hash — mitigated by chain continuation: the next entry's `prev` still references the original hash (`re-hashing a tampered entry`). (d) PII leak via `meta` — mitigated by an allowlist on the writer side (comes in G1-04); tests currently pass sanitized examples.
4. **Assumptions.** SHA-256 pre-image resistance holds. The private data repo history is retained (no force-push). Committee members hold accounts with 2FA (comes G3-01). The workstation running `just verify` is trusted.
5. **Follow-ups.** (a) Sign each entry with an ed25519 key held only in Actions secrets (arch §15.2 F-SC13) — planned for G1-04. (b) Publish daily tail-hash fingerprint to a public gist so tampering is externally observable. (c) Add a nightly Action that runs `verify(chain)` and opens an issue on failure.
